【批次十注记：本文件的历史段落已按新名字整体替换】
批次十做了一次全局命名规范化：英文标识符统一到 Scheduling / Schedule 词根，

--------------------------------------------------------------------------------
【为什么重跑】
上一版用单条正则
    public (class|interface|record|enum|event|Task|void|bool|int|string|IReadOnlyList|IReadOnlyCollection)
它会漏掉四类成员：
    1. 接口成员 —— 接口成员没有 public 修饰符（ILogService 的成员一个都没进）
    2. public static / public const / public readonly 字段
    3. public async Task 方法
    4. public sealed class / public partial class / public static class
本版改为「先扫所有以 public 开头的行，再用状态机补扫 public interface 块内的成员」，
不做类型白名单。

  遇到 4 空格缩进的 "}" 退出接口块；跳过注释行、空行与孤立 "{"，其余行即接口成员。

    targetType = "none" → targetValue = ""
  掩码值用 InvariantCulture 格式化：某些区域设置下 ulong.ToString() 会带千位分隔符
  （"65,280"），对端 ulong.Parse 直接抛异常。

  【与 save-scheduling-rule 入参格式**不对称**，这是有意的】
    保存时 targetValue 取 "CCD0" / "CCD1"（或 "0" / "1"）与**掩码 Id**；
    查询时给的是索引数字与掩码**值**。
    理由：查询要回答「这条规则现在绑到哪」，用值最直观，UI 不必反查 masks.json；
          保存要「绑到哪」，用 Id 才能让 Worker 把掩码名称一起快照进规则。
    推论：**「查出来 → 原样存回去」对 mask 类规则不成立**，UI 改掩码规则必须重新选一次掩码。
    这条不对称若在将来收敛，应同时改两端并提升 ProtocolVersion。

  【为什么不直接序列化 ScheduleRule】
    它是落盘模型：MaskId / MaskName 只在 Worker 内部有意义，Label 是派生属性。
    直接当协议模型用等于把 schedules.json 的字段演进绑死到 IPC 上。

【3. query-scheduling-rules（新增命令）】
  Payload：无（忽略）。
  返回：Success=true 时 Payload = JSON 数组（见 §2）。
  实现：PipeServerService.RunQuerySchedulingRules()（同步，不读盘）
        + BuildScheduleRulePayloads(IReadOnlyList<ScheduleRule>)（纯函数，可测）。

  【为什么不重读盘】
    schedules.json 的唯一写入方是本进程（save / delete 都立刻写盘并更新内存）。
    每次查询都 Load() 只是白做一次 IO，还会在文件被外部改坏时把内存里的正确状态
    覆盖成空表。这一点与 query-processes 的 `_scheduling.Load()` 不同 —— 那条命令
    算的是「命中规则名」，宁可重读也不能用旧规则；查询规则本身则应以内存为准。

  【save-scheduling-rule / delete-scheduling-rule 核实结论】
    两个命令在批次七已实装，本轮只核实，未改逻辑：
      · save：RunSaveScheduleRuleAsync —— 校验 processName / targetType / priority，
              写盘后调 _watcher.ReapplyNow()；
      · delete：RunDeleteScheduleRuleAsync —— 按进程名删除，写盘后调 _watcher.ReapplyNow()。
    两者都满足「写盘 + ReapplyNow」的成对要求，无需补齐。

【5. 场景规则的三个命令】
  · query-scenario-rules
      Payload：无。返回 Payload = JSON 数组（见 §4）。
      实现：RunQueryScenarioRules() + BuildScenarioRulePayloads(...)（纯函数）。
      **不含总闸**：ScenarioFile.Enabled 是「功能开没开」，与「有哪些规则」是两个问题；
      混进数组会让 UI 分不清「没有规则」和「有规则但总闸关着」。

  · save-scenario-rule
      Payload = JSON（见 §4）。**id 为空串 = 新建**。
      校验：profileId 非空且方案必须存在（否则命中时静默不动作）；
            Trigger=ProcessRunning 时 argument 必须非空；
            电源类触发（OnBattery / OnAcPower）的 argument 必须为空
            （Matches 用 argument 做相等比较，带值就永远不命中）；
            非空 id 必须是已存在的规则，否则失败（不静默改写成新建）。
      实现：RunSaveScenarioRuleAsync。

      【Id 为空时不能写 rule.Id = ""】
        ScenarioRule.Id 的属性初始化器会生成 Guid；赋空串会把它覆盖掉 ——
        结果是一条 Id 为空的规则：落盘后下一次 Save 又把它当新规则，
        列表里会长出一堆互相无法区分的空 Id 条目。
        因此代码是「new ScenarioRule()，仅在 id 非空时赋 rule.Id」，
        新建的 Id 由初始化器产生（32 位无横线 GUID）。
        ScenarioService.Save 本身**不**生成 Id，它只按 Id 做 upsert ——
        生成责任在模型初始化器，这一点在实现时必须清楚。

  · delete-scenario-rule
      Payload = 规则 Id（不是触发参数）。调 ScenarioService.Delete(id)；
      返回 false 时 Message 说明「规则不存在」。

【1. 删除 ShowTrayIcon：它其实是个只写字段】
  这是本批唯一「删了不心疼」的字段，原因不是它多余，而是它**从来没被读过**：
  全仓唯一的两处引用是声明本身与通用页的复选框绑定，托盘图标的创建逻辑
  （旧 App.OnStartup 的 `behavior == Tray || trayOnly`）从未看过它。
  也就是说用户勾掉「显示托盘图标」之后，界面记住了这个选择，程序行为一点没变。
  既然行为要改成「由两个开关共同决定」，留一个写进去没人读的键只会误导下一个人。

  【为什么不需要迁移】
  旧默认值是 true，但旧代码在 CloseBehavior=Exit 且没有 --tray 时同样不建托盘 ——
  新规则（AutoStartMode=WorkerWithTray 或 CloseBehavior=Tray）对所有旧配置给出的
  结果与旧行为一致，迁移只会制造一个用户没选过的状态。
  旧文件里的 showTrayIcon 键会被静默跳过（本工程没有配置 UnmappedMemberHandling.Disallow），
  下次 Save 自然消失。

【2. UiSettings 实现 INotifyPropertyChanged（public 面变更）】
  新增 public event PropertyChangedEventHandler? PropertyChanged。
  只在 AutoStartMode 与 CloseBehavior 的 setter 里广播，且值未变化时不广播。

  【为什么要广播，而不是让每个写入点各自通知托盘】
  这两个值有三个写入点：行为页的两个下拉、主窗口侧边栏的自启复选框、
  App.ChangeAutoStartAsync 的 IPC 成功路径。逐个去通知托盘，漏一处就是
  「设置改了、图标没跟着变」；而漏掉的那一处通常是最少走的那条路径，测试也测不到。
  改成属性变更即广播，托盘只需要订阅一次。

  【为什么不广播全部字段】
  主题 / 材质 / 动效改的是界面自身的呈现，由各自的绑定就地刷新，与进程生命周期无关。

  【值未变化时不广播的原因】
  开机自启保存失败时，ChangeAutoStartAsync 会把内存值回滚成原值再赋一遍。
  无脑广播会让托盘在那一次回滚里被销毁又重建，用户看到图标闪了一下。

  【落盘形状不变】
  事件不参与 JSON 序列化；两个属性仍以枚举名称落盘（JsonStringEnumConverter<T>）。
  持久化字段数 12 → 11。

【3. TrayPolicy（public，新增）与托盘生命周期】
  public enum TrayAction { None = 0, Create = 1, Dispose = 2 }
  public static class TrayPolicy
  {
      static bool       ShouldShowTray(AutoStartMode mode, CloseBehavior behavior);
      static TrayAction Decide(bool shouldShow, bool exists);
      static string     Describe(AutoStartMode mode, CloseBehavior behavior, bool exists);
  }

  ShouldShowTray = (mode == AutoStartMode.WorkerWithTray) || (behavior == CloseBehavior.Tray)

  【为什么放在 Core 而不是 UI】
  真正的资源是 WinForms 的 NotifyIcon，只有 UI 进程能持有；但「什么时候该有」
  是纯函数。放进 Core，测试工程（只引用 Core + Worker）就能直接钉住
  「条件为真 → 建 / 条件为假 → 撤 / 重复调用幂等」三条分支，不必拉起 WPF 进程。

  【为什么是三值 TrayAction 而不是 bool】
  用 bool 表达会出现「每次刷新都 Dispose 一遍再重建」的实现，用户能看到图标在闪。

  【UI 侧：TrayManager（internal，不在本文件冻结范围，仅备查）】
  RefreshTrayState(bool forceShow = false) 是托盘的**唯一**出口：
    · 条件为真且无图标 → 创建；条件为假且有图标 → 销毁；
    · 销毁前若 Application.MainWindow 为 null，**先恢复窗口再销毁** ——
      Tray 模式下关窗口是销毁（不是隐藏），先撤图标会留下一个既无窗口、
      也无图标、还退不掉的进程；
    · App.OnStartup 调用一次 RefreshTrayState(trayOnly)，并订阅
      UiSettings.PropertyChanged 在变化时再次调用；
    · App.OnExit 与启动失败路径调用 DisposeTray()（无条件回收，不做窗口恢复）。
  旧 App._trayIcon 字段与 OnStartup 里的托盘分支已整体删除，不保留旧分支。

  【forceShow 为什么必要】
  --tray 是一次启动的临时形态，不属于持久化设置，TrayPolicy 看不到它。
  用户手工 `Zentwik.UI.exe --tray` 且 ui.json 为「不自启 + 关窗口即退出」时，
  纯按设置判断会得出「不要托盘」——进程既无窗口也无图标，只能去任务管理器杀。

【4. ApplyProcessPriorityPayload（public sealed class，新增）与 apply-process-priority】
  Payload = {"pid":1234,"processName":"msedge.exe","priority":"High"}
    pid          必须是正整数；
    processName  身份校验用，空白一律拒绝；
    priority     必须是 ProcessPriority.Options 里的英文常量（大小写不敏感），空串拒绝。

  返回：
    Success=true   → Message = "已把 {名字}（PID {pid}）设为 {中文档位}"
    Success=false  → Message ∈ {
        "进程已变更，请刷新列表"           （pid 不存在 / 名字不符 / 句柄拿不到）
        "未知的优先级档位：…"               （priority 不合法）
        SetPriorityClass 的原文（含 Win32 错误码）
        "pid 必须是正整数…" / "processName 不能为空…" / "Payload 不是合法 JSON：…"
    }

  【为什么必须校验名字】
  从 UI 采样到用户点「应用」之间有一段延迟，短命 PID 可能已被回收并分配给另一个进程。
  只按 pid 下发，就会把一个用户没选过的程序设成 High —— 这类错误用户无法归因，
  比「操作失败」糟糕得多。

  【名字比对口径】
  两边都去首尾空白、去 .exe 后缀（大小写不敏感），因为 Process.ProcessName 不含扩展名，
  而 schedules.json / 进程页显示 / 用户手打的名字都带 .exe。只要有一边不归一化，
  比对永远不相等，表现为「每次应用优先级都说进程已变更」。
  归一化函数：PipeServerService.NormalizeProcessName（internal static）。
  提示语常量：PipeServerService.ProcessChangedMessage（internal const）。

  【进程已退出不算异常】
  Process.GetProcessById 在进程不存在时抛 ArgumentException、句柄拿不到时抛
  Win32Exception，两者都是「用户点得慢了」的正常竞态，统一翻译成同一句提示，
  不把 .NET 异常类型名泄露到界面上。其余异常照实回报，不伪装成「进程已变更」。

  【为什么不落盘】
  这是一次性动作，不是规则。需要持久化的场景走 save-scheduling-rule 的 priority 字段。

【5. ScheduleRule.Id（public 面变更）】
  public string Id { get; set; } = Guid.NewGuid().ToString("N");   // 32 位无横线 GUID

  【为什么现在必须有 Id】
  业务键一直是进程名（同名唯一、同名覆盖），删除也只传名字。这在「一个进程一条规则」
  的前提下够用，但界面一旦要支持「选中某一行、编辑、再删掉它」，名字就不够用了：
  用户在编辑框里改了进程名，那一行的身份就跟着变了 —— 按名字删会删不到（已改名），
  按名字改会多出一条（新旧名字都在）。Id 把「这条记录是谁」与「它绑哪个进程」分开。

  【旧配置文件怎么办】
  老 schedules.json 里没有 id 键，缺键时属性初始化器给的是一个**本次进程内**的随机 Guid，
  下次读盘又是另一个。因此 SchedulingStore.MigrateLegacyNames 在读盘时给空 Id 补一个，
  并随下一次 Save 落盘 —— 否则「查出来的 Id 拿去删」这条链路在重启后就断了。

  【为什么不是 int 自增】
  schedules.json 会被多台机器 / 多次重装共享（用户直接拷配置目录）。自增序号必然撞号，
  而撞号的后果是删错规则。

  【覆盖时保留原 Id】
  save-scheduling-rule 覆盖已有规则时执行 rule.Id = rules[index].Id：Id 是「这条记录是谁」，
  保存一次不该换一个身份，否则界面刚拿到的 Id 立刻失效，下一次按 Id 删除就会 404。

【6. delete-scheduling-rule 的 Payload 语义变更】
  旧：Payload = 进程名（如 msedge.exe，忽略大小写与首尾空白）
  新：Payload = 规则 Id；匹配不到时**退回**按进程名匹配

  【为什么保留名字回退】
  旧 UI 只会发名字，而升级途中新旧两个 exe 混搭是常态。把旧写法直接判错，
  表现就是「点了删除、规则还在、只弹一句协议错误」。
  回退是单向的：Id 一旦命中就绝不再看名字，不做二义性猜测。

【7. save-scheduling-rule 的匹配顺序与新增字段】
  Payload 新增两个可选字段：
    id      留空 = 按进程名新增或覆盖（旧版行为）；非空且命中 = 就地更新那一条
    enabled 留空（null）= 保持原值（新建时按启用）；false = 禁用

  【为什么补 enabled】
  query-scheduling-rules 一直返回 enabled，而保存侧没有对应入参，
  于是「查出来 → 改一个字段 → 存回去」这条路走不通：任何一次保存都会把
  一条已禁用的规则悄悄改回启用。协议两个方向必须能对上。
  用 bool? 而不是 bool：false 与「没传」是两件事。

  【匹配顺序】
  先按 id 找；找不到（旧 UI 不传 id，或那条规则刚被别处删掉）再按进程名找；
  都没找到就追加。这一步同时保证了「同名规则只有一条」这条业务不变量。

【1. 为什么整批改名，而不是只改对外面】
  旧名字有两层问题，且互相放大：
    · 英文侧同一个概念有三套词根，同一个动作在不同文件里长得不一样，
      搜代码时必须把三个词都搜一遍才敢说「改全了」；
    · 中文侧旧称是个自造缩写，用户看不懂，开发者也要先解释一遍才明白。
  统一到 Scheduling / Schedule / 调度 之后，一条 grep 就能定位整个概念面。
  这是一次性成本，拖着只会让后面每一批都在旧词上再加新代码。

【2. 精确映射（只列有语义分歧的几条）】
  · ScheduleRule.Mask → TargetMask
      属性名从「一个叫 Mask 的东西」变成「目标的掩码值」，与 Target / TargetMask
      枚举成员形成一组：Target 说「哪一类」，TargetMask 说「那个值」。
      注意 CustomMask.Mask（掩码库里的那条记录）**没有改名** —— 它是掩码自己的值，
      与规则的调度目标无关。禁止把 MaskStore / CustomMask / MaskFormatter 卷进来。
  · SchedulingTarget.Custom → TargetMask
      旧名说的是「自定义」，但真正的区分点是「有没有掩码」，不是「谁定义的」。
  · Unbind(pid) → ClearSchedule(pid)
      Unbind 的宾语是被绑定的进程，改叫 ClearSchedule 后宾语是调度本身，
      与 ScheduleTo* 形成「设 / 清」的一对，读起来不再需要脑补主语。
  · 清空全部调度的那个命令常量也一并改名（对应字符串改成 clear-all-schedules）
      它不在原始映射表里，但验收要求旧常量名零命中，常量名必须跟着走；
      既然本批裁定「无需兼容」，线上字符串一并改成同名形态，避免常量与字符串两张皮。

【1. 新增命令（2 条）】
  CommandQueryPowerPolicy = "query-power-policy"
      参数：无（Payload 忽略）。
      返回：Success = true（**查询本身**成功，不表达目标可用性），
            Payload = JSON PowerPolicySnapshot。
      「读不到活动方案」仍然是 Success = true：它是快照的内容
      （五项 Supported=false + Error），不是查询失败。与 query-smu-status 同一口径。
  CommandApplyPowerPolicy = "apply-power-policy"
      参数：Payload = JSON ApplyPowerPolicyPayload（五个字段全部可空，null = 不改）。
      返回（六种形态，全部穷举，没有第七种）：
        ① 全部成功且激活成功
             Success = true
             Message = "已应用 {N} 项电源策略"
             Payload = 写入后的快照（重读失败时为 null，兜底口径同 ⑤⑥）
        ② Payload 缺失 / null / 五个字段全 null
             Success = false
             Message = "没有要修改的字段"
             Payload = null
        ③ JSON 非法（反序列化抛 JsonException）
             Success = false
             Message = "请求格式错误：{异常信息}"
             Payload = null
             **不得**掉进 ② 分支（两者原因不同：请求坏了 vs 请求合法但空）
        ④ 一项都没写成（全部被范围校验或 API 拒绝）
             Success = false
             Message = 逐项错误用逗号连接，例：
                       "能效偏好（EPP）写入失败（错误 87），ASPM 写入失败（错误 87）"
             Payload = null（系统里什么都没变，没有快照可回）
        ⑤ 部分成功且激活成功
             Success = false
             Message = "部分字段写入失败：{逐项错误摘要}"（摘要内部用逗号）
             Payload = 写入后的快照（**失败也要回**，供 UI 刷新界面）
        ⑥ 至少一项写成功、但激活失败
             6a 无逐项错误：Message = "配置已写入但激活失败，请重启系统后生效"
             6b 有逐项错误：Message = "{逐项错误摘要}；配置已写入但激活失败，请重启系统后生效"
                 （摘要内部用逗号，两类信息之间用分号；6b **不加**「部分字段写入失败：」前缀）
             Success = false
             Payload = 写入后的快照

      【分隔符规则：内逗号、外分号】
        逐项错误之间用「，」；「逐项错误」与「激活失败」两段之间用「；」。
        共用一种分隔符时，读的人无法判断后面那句是第三项错误还是整批操作的另一类失败。

      【Payload 兜底】
        ⑤⑥ 两条失败路径都要重读快照；重读失败时 Payload = null。
        判定「重读失败」包含两种情况：抛异常，或读回来是降级快照
        （ActiveSchemeGuid == Guid.Empty）—— 后者说明连方案都拿不到了，
        拿一份「五项全不支持」的数据去覆盖界面比回 null 更误导。

      【为什么失败也要回 Payload】
        只要有至少一项写成功，系统里的值就已经变了。UI 拿着旧值画界面，
        用户会看到「提示失败、滑块还停在旧位置」，下一次点应用又会把已生效的项重写一遍。
  位置：Zentwik.Core/Ipc/WorkerPipeContract.cs（接在 CommandDeleteScenarioRule 之后）。

【2. PowerPolicySnapshot（public sealed class，新增）】
  命名空间 Zentwik.Core.Services。
  字段（JSON 名 → C# 名）：

      activeSchemeName        → ActiveSchemeName (string)

【3. ApplyPowerPolicyPayload（public sealed class，新增）】

【4. IPowerPolicyApi（public interface，新增）+ PowerPolicyApi（public sealed，新增）】

【9. ReadFriendlyName 的编码解析已抽成可测方法】
  PowerPolicyApi.ParseFriendlyName(IntPtr buffer, uint byteCount) —— internal static。
  · 按字节数限长读取，不依赖「PtrToStringUni 会在 \0 处停下」：
    带长度参数的重载是「复制指定个数的字符」，而 API 写出的长度是**含**结尾符的，
    不截断会让方案名带上一个看不见的 U+0000（界面看不出异常，但它与任何字面量都不相等）。
  · 空指针 / 不足一个字符 / 全空白 → null。
  · 单测用自造缓冲区覆盖（UTF-16 正常、超长声明、截断、空指针、全空白），
    不必改真实电源方案的名字。
  · 实机验证：读回 name=[平衡] len=2（无尾随零字符）。
